# zkTalk UI E2E Plan (2026-04-01)

Status: proposed execution plan
Audience: engineering / QA

## Why this plan exists

zkTalk already has strong API regression coverage and useful desktop/mobile harness scripts, but it does not yet have a real browser-driven UI E2E layer for the web app, and desktop/mobile UI confidence still leans heavily on manual smoke checks.

The goal of this plan is to add a strong UI-first E2E stack that:

- catches broken user workflows, not just broken endpoints
- verifies that cross-surface collaboration behavior is visible in the UI
- keeps CI fast for core flows and deeper for nightly / pre-release runs
- reduces dependence on manual smoke for repeatable regressions

## Current reality

What already exists:

- API multi-user regression: `apps/api/scripts/two-user-messaging-e2e.mjs`
- Desktop harness regression: `scripts/desktop-harness-regression.mjs`
- Mobile harness regression: `scripts/mobile-harness-regression.mjs`
- Manual smoke checklist: `docs/manual-smoke-checklist-2026-03-27.md`

What is missing:

- no checked-in `e2e/` directory
- no Playwright config or browser UI runner
- no stable shared UI fixture/seeding layer for browser-driven tests
- limited stable selectors for complex flows such as composer actions, context menus, dialogs, unread chips, and moderation actions

## Test strategy

Use three complementary UI automation layers instead of trying to force one tool onto everything.

### 1. Web UI E2E: Playwright

Primary purpose:

- cover the real Next.js UI end to end
- verify high-value workflows fast enough for CI
- cover most collaboration flows without Electron or mobile runtime overhead

Why:

- fastest feedback
- easiest DOM assertions
- best fit for chat, settings, friends, community creation, moderation, inbox, bookmarks, and most attachment flows

### 2. Desktop shell E2E: Playwright + Electron smoke

Primary purpose:

- verify desktop-only shell behavior that plain web E2E cannot prove
- check protocol handoff, session override, startup route handling, packaged/dev shell parity

Why:

- the desktop app mainly wraps the web app, so most product coverage belongs in web Playwright
- only shell-specific flows need Electron coverage

### 3. Mobile UI E2E: Maestro first, keep simulator harness

Primary purpose:

- cover the most important mobile-only UX paths
- verify actual taps/navigation on simulator builds
- reuse existing simulator harness and screen test IDs

Why not start with Detox:

- Detox is viable later, but Maestro is lighter to stand up quickly for Expo-style flows
- zkTalk already has simulator harness support that pairs well with scripted mobile driving

## Suite shape

Organize tests by product risk, not by file tree.

### `smoke`

Must pass on every PR.

Goals:

- login works
- app loads
- messaging still works
- core navigation still works
- profile/settings save works

Target runtime:

- under 10 minutes total

### `collab`

Run on merge or nightly.

Goals:

- friend and invite flows
- event, poll, forum, bookmark, inbox flows
- DM promotion and source-history behavior
- attachment preview and persistence

### `admin`

Run on merge or nightly.

Goals:

- moderation
- permissions
- audit log
- community settings
- member actions and role boundaries

### `shell`

Desktop-specific.

Goals:

- deep-link startup
- session-token handoff
- desktop harness route behavior

### `mobile`

Simulator-driven.

Goals:

- mobile login and navigation
- channel/DM messaging
- create community/channel
- friend and QR-adjacent entry points
- profile/edit/settings

## P0 web/desktop smoke scope

These are the first tests to implement. They give the highest confidence per minute.

### Auth and session

- login by email in dev flow
- login by phone/OTP in dev flow
- logout returns to login page
- protected route redirects to login when session is absent
- login honors `next` redirect

### Core navigation

- home loads joined communities
- community click opens the expected channel
- channel sidebar navigation changes the active room
- DM list opens a conversation
- inbox item opens the right destination

### Channel messaging

- send a plain text message
- receive a seeded external message and see it render in UI
- edit a sent message
- delete a sent message
- add and remove a reaction
- open thread from a message and reply

### DM messaging

- create a direct DM from friends UI
- send and receive in DM
- upload an attachment in DM
- confirm attachment remains visible after reload/re-entry

### Profile/settings

- edit display name and bio
- select a profile image and verify it is not persisted until `Save`
- save the profile image and confirm avatar refresh in rail/header

### Community creation and entry

- create a community from `/communities/new`
- verify slug behavior for editable/manual slug
- join via invite code from home header

## P1 collaboration scope

Add these once P0 is stable.

### Friends and sharing

- open shared profile from pasted text/link
- send friend request
- accept friend request
- jump from friend card to DM

### Inbox and bookmarks

- mention creates inbox item
- opening inbox item marks it read and lands at target
- bookmark a message and reopen it from bookmarks

### Events

- create event
- RSVP from another user
- open attendees
- start DM from attendees list

### Polls and forum

- create poll
- vote and unvote
- create forum post
- reply to forum post

### DM promotion

- promote a group DM to a private community
- original DM becomes read-only
- promoted channel exposes source DM history entry point
- DM list routes to promoted destination

### Attachments and preview UX

- channel image shows preview without extra click
- file attachment can be opened/downloaded
- preview survives navigation away and back

## P2 admin and permission scope

### Moderation

- create report
- resolve report
- dismiss report
- audit log shows the right entries

### Role boundaries

- moderator can access reports but not owner-only audit behaviors
- admin gains elevated access
- owner-only delete stays owner-only

### Member actions

- mute removes posting ability
- kick removes active membership and public rejoin still works
- ban blocks rejoin

### Community settings

- update community name/description
- toggle visibility to `invite_only`
- toggle visibility to `private`
- direct join and discover behavior matches the setting

## Desktop shell scope

Keep this intentionally small.

### Must automate

- app launches into correct route
- protocol URL is consumed
- session token from desktop handoff overrides stale browser session
- desktop harness page posts a message then redirects into channel/DM

### Do not over-invest here

- ordinary chat UI, settings UI, and moderation UI should be covered in web Playwright unless the Electron shell changes behavior

## Data and fixture strategy

UI E2E will be flaky unless test data is deterministic.

### Recommended fixture model

Create one test seeding entrypoint that returns:

- `ownerUser`
- `memberUser`
- `moderatorUser`
- `thirdUser`
- `community`
- `chatChannel`
- `forumChannel`
- `voiceChannel`
- `directConversation`
- `groupConversation`
- `inviteCode`
- optionally pre-seeded `event`, `poll`, `bookmarkableMessage`, `threadRoot`

### Rules

- every test file gets a fresh namespace or seed prefix
- seed through API or a dedicated test setup route, not through the UI
- cross-user assertions should use two authenticated browser contexts
- long collaborative scenarios should prefer seeded state plus one or two UI actions, not full setup via clicks

## Selector strategy

Current UI has some accessible labels and a few test IDs, but not enough for stable E2E.

Add explicit selectors to these areas first:

- login tab switchers and submit buttons
- OTP inputs and dev-token/dev-code reveal area
- community list items and create/join controls
- channel list items and active channel markers
- composer textarea, send button, attachment button, emoji button, schedule button
- message row container keyed by message id
- message action buttons: reply, thread, copy, edit, delete, react
- inbox item rows
- bookmark item rows
- friend request actions
- event attendee DM action
- moderation report cards and action buttons
- role/member action menus
- visibility radio groups and save buttons
- source-DM badges and promoted-DM read-only banners

Selector rule:

- prefer `data-testid` for volatile or repeated UI
- keep semantic roles and labels for user-facing controls
- never rely on styling classes or raw text alone for core assertions

## CI plan

### PR gate

- API regression
- web `smoke`
- desktop `shell` mini smoke

### Merge / nightly

- web `collab`
- web `admin`
- mobile `P0` and selected `P1`
- desktop packaged-shell regression

### Pre-release

- full manual smoke
- real-device Korean IME pass
- voice/video assisted validation

## Recommended implementation order

1. Create `e2e/` workspace with Playwright config and basic auth fixture helpers.
2. Add stable selectors to the existing web UI.
3. Build deterministic API seeding for users/community/channel/DM.
4. Implement the `P0 smoke` web suite.
5. Add the small Electron shell suite.
6. Expand to `P1 collab`.
7. Add `P2 admin`.
8. Stand up Maestro mobile smoke on top of existing simulator harness.

## First concrete milestone

The first milestone should deliver these 8 tests:

- email login and redirect
- phone login and OTP verify
- home -> community -> channel navigation
- channel send/edit/delete
- thread open and reply
- DM send/receive
- inbox mention open
- profile photo change requires explicit save

If these 8 are green and stable, zkTalk will already have far stronger UI confidence than it has today.

## Risks to watch

- websocket timing and unread state can cause race conditions unless assertions wait for visible UI state
- attachment uploads need retry-aware helpers and cleanup
- desktop startup-route handling is already known to be flaky on cold launch and should stay in its own suite
- mobile should not block core web PR confidence until its runtime automation is stable

## Definition of success

This plan is working when:

- a broken user-visible chat flow fails in UI automation before manual smoke catches it
- profile/settings/navigation regressions are caught without relying on human QA memory
- desktop-specific regressions are isolated to shell tests
- manual smoke shrinks to release-polish and native-edge cases instead of rechecking routine chat flows
